# BetterTouchTool Action JSON Definition Reference

This document provides a reference for BetterTouchTool action JSON and how to define them via JSON. Actions are configured using the `BTTPredefinedActionType` field with the corresponding action ID.

Coverage is partial. For AI configuration, `lookup_btt_action_definition(action_id)` also returns key locations and constraints from the running app's native schema. Validate JSON with `validate_btt_trigger_json`, then inspect the exported result after a write. A validation pass checks structure and covered fields; it does not prove that every legacy option or runtime behavior is correct.

## Important Notes

### JSON Format
- JSON objects will be automatically recognized on import - you don't need to escape them as strings
- Fields that accept JSON objects (like `BTTGenericActionConfig`, `BTTAdditionalActionData`, etc.) can be provided as regular JSON objects instead of escaped strings

### Common Fields
- **BTTAdditionalActionData**: Many actions support this field for extended configuration options. It contains a JSON object with action-specific properties
- **BTTGenericActionConfig**: Used for simple configurations, can be a string or JSON object depending on the action
- **BTTGenericActionConfig2**: Secondary configuration field when additional data is needed

### Custom Click (Custom Mouse Buttons & Modifiers)

> Performs custom mouse clicks with various options including button type, modifiers, and click behavior.

Parameters:
* **BTTPredefinedActionType**: 119
* **BTTCustomClickConfig**: string with the raw click configuration (alternative low-level format). Three digits `[left][middle][right]`, optionally followed immediately by the decimal macOS modifier bitmask, where each digit is the click count for that button (1=single, 2=double, 3=triple). Common values: `"100"` left click, `"200"` double left, `"300"` triple left, `"010"` middle, `"001"` right, `"500"`/`"600"`/`"700"`/`"800"`/`"900"` = buttons 4-8, `"-300"` = button 3
* **BTTCustomClickUpDownConfig**: string - `"0"` = down and up (normal click), `"1"` = down only, `"2"` = up only (optional)
* **BTTAdditionalActionData**: JSON object (optional)
  - `BTTCustomClickIncludePressedModifiers`: boolean - include currently pressed modifiers
  - `BTTCustomClickSendToHoveredWindow`: boolean - if true, routes the click to the window currently under the mouse cursor (even if that window is not focused)

Use these persisted keys for trigger creation and updates. The scripting-only convenience keys `BTTClickType`, `BTTModifiers`, `BTTIncludePressedModifiers`, and `BTTClickDownUpConfig` are not accepted by the trigger importer.

Example 1 - Left Click + Shift + Command (modifier mask 1179648):
```json
{
  "BTTPredefinedActionType": 119,
  "BTTCustomClickConfig": "1001179648",
  "BTTCustomClickUpDownConfig": "0"
}
```

Example 2 - Right Click with physically pressed keys:
```json
{
  "BTTPredefinedActionType": 119,
  "BTTCustomClickConfig": "001",
  "BTTCustomClickUpDownConfig": "0",
  "BTTAdditionalActionData": {
    "BTTCustomClickIncludePressedModifiers": true
  }
}
```

Example 3 - Middle Click, Down-Only, with Shift:
```json
{
  "BTTPredefinedActionType": 119,
  "BTTCustomClickConfig": "010131072",
  "BTTCustomClickUpDownConfig": "1"
}
```

Example 4 - Alternative format using BTTCustomClickConfig:
```json
{
  "BTTPredefinedActionType": 119,
  "BTTCustomClickConfig": "200",
  "BTTAdditionalActionData": {
    "BTTCustomClickIncludePressedModifiers": true
  }
}
```

Example 5 - Left Click routed to the window currently under the cursor (without focusing it):
```json
{
  "BTTPredefinedActionType": 119,
  "BTTAdditionalActionData": {
    "BTTCustomClickSendToHoveredWindow": true
  },
  "BTTCustomClickConfig": "100",
  "BTTCustomClickUpDownConfig": "0"
}
```

### Move Mouse To Position

> Moves the mouse cursor to a specific position on screen.

Parameters:
* **BTTPredefinedActionType**: 153
* **BTTMoveMouseToPosition**: Position coordinates as "x,y" (legacy)
* **BTTMoveMouseRelative**: 1 for relative movement, 0 for absolute (legacy)
* **BTTAdditionalActionData**: JSON object with all mouse movement configuration
  - `BTTMouseMoveX`: X coordinate position
  - `BTTMouseMoveY`: Y coordinate position
  - `BTTMouseMoveUnitX`: X unit type (0=px absolute, 1=% of window width, 2=% of screen width)
  - `BTTMouseMoveUnitY`: Y unit type (0=px absolute, 1=% of window height, 2=% of screen height)
  - `BTTMouseMoveAnchor`: Reference point for position (see below for values)
  - `BTTMouseMoveDuration`: Animation duration in seconds. When omitted or at most 0.01, the cursor moves immediately.
  - `BTTMouseMoveWithoutPressedModifierKeys`: boolean - ignore currently pressed modifiers
  - `BTTMouseMoveScreenNameOrUUID`: Target screen identifier (for named screen anchors)
  - `BTTMouseMoveDragType`: 0 = move without dragging, 1 = drag with the left button, 2 = drag with the middle button
  - `BTTMouseMoveContinueDrag`: boolean - continue existing drag
  - `BTTMouseMoveRelativeVariableName`: Variable name containing a saved position (used with anchor 23)

Anchor values:
- 0: Default - Global position (origin top left corner of main screen)
- 1-4: Relative to corners of active window (1=top left, 2=top right, 3=bottom left, 4=bottom right)
- 5: Relative to center of active window
- 6: Relative to current mouse cursor position
- 7-10: Relative to text cursor position (7=top left, 8=top right, 9=bottom left, 10=bottom right)
- 11-15: Relative to focused element (11=top left, 12=top right, 13=bottom left, 14=bottom right, 15=center)
- 17: Relative to window default button center
- 18: Relative to window cancel button center
- 20: Relative to center of text cursor
- 21: Relative to saved mouse cursor position (variable: saved_mouse_position)
- 22: Relative to found image location (variable: image_location)
- 23: Relative to position saved in variable with name (uses BTTMouseMoveRelativeVariableName)
- 1001-1003: Relative to corners of main screen (1001=top right, 1002=bottom left, 1003=bottom right)
- 1004-1007: Relative to corners of screen with mouse
- 1008-1011: Relative to corners of screen with name

Example:
```json
{
  "BTTPredefinedActionType": 153,
  "BTTAdditionalActionData": {
    "BTTMouseMoveX": 100,
    "BTTMouseMoveY": 50,
    "BTTMouseMoveUnitX": 1,
    "BTTMouseMoveUnitY": 1,
    "BTTMouseMoveAnchor": 5,
    "BTTMouseMoveDuration": 0.3
  }
}
```

### Set Trackpad / Magic Mouse Pointer Speed

> Scales the pointer speed of Apple trackpads and the Magic Mouse. Trackpads keep the macOS pointer acceleration curve; the Magic Mouse adjusts Apple's native tracking setting instead.

Parameters:
* **BTTPredefinedActionType**: 696
* **BTTAdditionalActionData**: JSON object with pointer speed configuration
  - `BTTApplePointerSpeedDevice`: string - Target device: `"trackpad"` (default), `"magicMouse"`, or `"both"`.
  - `BTTApplePointerSpeedOperation`: string - `"set"` (default) applies the multiplier, `"reset"` returns the device to the macOS speed (1×).
  - `BTTApplePointerSpeedMultiplier`: number - Speed multiplier, minimum `0.5` (default: 1). Only used when the operation is `"set"`. `1` corresponds to the current macOS pointer speed.

`"trackpad"` covers built-in trackpads and Magic Trackpads; `"magicMouse"` covers Apple Magic Mice only. Other mice are not affected — use Change Mouse Speed And Acceleration (559) for those.

Trackpads scale the macOS pointer acceleration curve, so the multiplier applies evenly. The Magic Mouse instead adjusts Apple's native tracking setting, which interpolates between built-in curves: the resulting speed change varies with how fast the mouse is moved and only approaches the requested factor at higher settings.

The action stops without changing anything if the device or operation value is not one of the values listed above, or if the operation is `"set"` and the multiplier is missing, not a number, or below `0.5`. The configuration UI offers a slider up to 20×; higher multipliers can be entered manually. A multiplier the device cannot represent (too high, or — on a Magic Mouse already at a low native setting — below its minimum) leaves the current speed unchanged and only shows a status message in the settings.

The chosen multiplier is stored in BetterTouchTool's own settings (the same values as the Trackpad and Magic Mouse settings pages) and is reapplied to matching devices as they connect. It only takes effect while BetterTouchTool is running: the original settings are restored when BetterTouchTool quits and while the Mac sleeps, and the multiplier is reapplied on wake. `"reset"` removes BetterTouchTool's override and is equivalent to setting the multiplier back to 1. If another utility changes the same pointer setting, BetterTouchTool stops managing that device until the speed is set explicitly again.

Example (double trackpad pointer speed):
```json
{
  "BTTPredefinedActionType": 696,
  "BTTAdditionalActionData": {
    "BTTApplePointerSpeedDevice": "trackpad",
    "BTTApplePointerSpeedOperation": "set",
    "BTTApplePointerSpeedMultiplier": 2
  }
}
```

Example (reset both devices to the macOS speed):
```json
{
  "BTTPredefinedActionType": 696,
  "BTTAdditionalActionData": {
    "BTTApplePointerSpeedDevice": "both",
    "BTTApplePointerSpeedOperation": "reset"
  }
}
```

### Pick Color On Screen And Write To Clipboard

> Opens a color picker to select a color from anywhere on screen and writes the result to the clipboard in a configurable format. The color is additionally saved to the variable `last_picked_color` as JSON (r, g, b, a) so it can be transformed via scripting.

Parameters:
* **BTTPredefinedActionType**: 546
* **BTTLaunchPath**: string (optional) - Clipboard color format: `"0"` = CSS RGBA (default), `"1"` = HEX RGB, `"2"` = HEX RGBA, `"3"` = SwiftUI Color, `"4"` = NSColor Objc, `"5"` = UIColor Objc, `"6"` = NSColor Swift, `"7"` = UIColor Swift, `"8"` = CSS HSL, `"9"` = CSS HSLA

Example (copy as CSS HSL):
```json
{
  "BTTPredefinedActionType": 546,
  "BTTLaunchPath": "8"
}
```

### Send Keyboard Shortcut

> Sends a keyboard shortcut to the system - just as if you had pressed it on your keyboard.

Parameters:
* **BTTPredefinedActionType**: 264
* **BTTShortcutToSend**: Key codes as comma-separated string. Format: modifier key codes (sorted highest to lowest), then standard key code. Import also accepts common human-readable strings like `"cmd+shift+s"`, `"⌘⇧S"`, or `"command option d"` and converts them to key-code format.
* **BTTShortcutModifierKeys**: Not used for shortcut actions. Include modifiers directly in `BTTShortcutToSend`.
* **BTTShortcutUpDown**: Optional - "onlyDown" to send only key down event, "onlyUp" to send only key up event
* **BTTAdditionalActionData**: JSON object (optional)
  - `BTTActionSendKeyboardShortcutIncludeCurrentModifiers`: boolean - include currently pressed modifier keys when sending the shortcut
  - `BTTActionSendKeyboardShortcutLowLevel`: boolean - send the keyboard shortcut at the lowest possible system level (HID event tap instead of session event tap). Useful when the shortcut is not recognized by certain apps at the default level

Example:
```json
{
  "BTTPredefinedActionType": 264,
  "BTTShortcutToSend": "63,59,58,56,55,49"
}
```

To only send the key down event:
```json
{
  "BTTPredefinedActionType": 264,
  "BTTShortcutToSend": "63,59,58,56,55,49",
  "BTTShortcutUpDown": "onlyDown"
}
```

### Send Shortcut to Specific App

> Sends a keyboard shortcut to a specific application.

Parameters:
* **BTTPredefinedActionType**: 128
* **BTTShortcutToSend**: Key codes as comma-separated string (same format as Send Keyboard Shortcut). Import also accepts common human-readable strings like `"cmd+s"` and converts them to key-code format.
* **BTTShortcutApp**: Bundle identifier or path of the target app, or `"active app"` to target the currently active/frontmost app, or `"app under mouse cursor"` to target the app under the mouse cursor
* **BTTShortcutSwitchToAppFirst**: 1 to switch to app first, 0 otherwise
* **BTTShortcutAppUnderCursor**: Set to `"app under mouse cursor"` for app-under-cursor mode, or `"active app"` for active-app mode (optional)

Example (send to specific app):
```json
{
  "BTTPredefinedActionType": 128,
  "BTTShortcutToSend": "55,1",
  "BTTShortcutApp": "com.apple.finder",
  "BTTShortcutSwitchToAppFirst": 1
}
```

Example (send to active/frontmost app):
```json
{
  "BTTPredefinedActionType": 128,
  "BTTShortcutToSend": "55,1",
  "BTTShortcutApp": "active app",
  "BTTShortcutAppUnderCursor": "active app"
}
```

### Move / Resize Window to Custom Position and Size

> Formerly named "Custom Move / Resize Window". Moves and/or resizes a window with a fully custom configuration: which window, which monitor, where to place it (anchor + offset) and how to size it. Configured via an inline form in BTT (legacy sheet available via the `BTTUseLegacyMoveResizeConfig` default).

Parameters:
* **BTTPredefinedActionType**: 251
* **BTTActionMoveResizeName**: string (optional) - Custom name for this configuration
* **BTTActionMoveResizeConfig**: string - The configuration as a JSON *string* (it is stored in the trigger's launch path, so the object must be serialized, not nested). Keys:
  - `BTTMoveResizeVersion`: number - `3` for configurations written by the inline form. Version-less configs keep the exact legacy behavior; version `2` enables two small executor fixes (bottom-left window anchor, consistent target screen for "keep current position"); version `3` routes the whole computation through the new engine and unlocks all keys marked *(v3)* below. Use `3` for new configurations
  - `BTTActiveOrHoveredWindow`: number - window to move: `0` = focused window, `1` = window under mouse cursor, `2` = window(s) with title matching `BTTTitleToMatch` (wildcards `*` allowed, ALL matching windows are moved), `3` = the n-th window in front (`BTTWindowZIndex`, `1` = frontmost)
  - `BTTTitleToMatch`: string (mode 2), `BTTWindowZIndex`: number (mode 3)
  - `BTTScreensToMove` + `BTTOriginDisplay`: numbers - target monitor. `BTTScreensToMove` `0` = stay on the start monitor (`BTTOriginDisplay` `1` = monitor the window is on, `2` = main monitor, `3` = monitor with the mouse cursor), `-1` = monitor with the mouse cursor, `-2` = monitor with the exact frame `BTTSpecificScreenFrame` (NSStringFromRect format, e.g. `"{{0, 0}, {1920, 1080}}"`), `-3` = specific monitor by `BTTScreenUUID`, `-4` = built-in display *(v3)*, `-5` = display with the Dock *(v3)*, `N >= 1` = move N monitors in direction `BTTDirectionToMove` starting from `BTTOriginDisplay`
  - `BTTReferenceKind` *(v3)*: number - what anchors, percentages and grid cells refer to: `0` = the target monitor (default), `1` = the focused window, `2` = the window under the mouse cursor, `3` = a specific window (`BTTReferenceWindowTitle` with wildcards, optional `BTTReferenceWindowApp` = app name or bundle id), `4` = a rectangle stored in the variable `BTTReferenceVariable` (value formats: `"x,y,width,height"`, `"{{x, y}, {width, height}}"` or JSON `{"x":..,"y":..,"width":..,"height":..}`, screen coordinates with top-left origin), `5` = the window directly behind the focused window in z-order (any app; useful when the focused window is the one being moved). For kinds 1-5 the target monitor is the one containing the reference
  - `BTTMargin` + `BTTMarginUnit` *(v3)*: numbers - inset applied to the reference area before placing (unit `0` = px, `1` = % of the smaller side)
  - `BTTPlacementMode` *(v3)*: number - `0` = anchor + offset (below), `1` = grid cell: `BTTGridColumns`, `BTTGridRows`, `BTTGridColumn`, `BTTGridRow` (1-based), `BTTGridColumnSpan`, `BTTGridRowSpan`, `BTTGridGap` (px between cells). `BTTGridAutoAssign`: `1` gives every window of a multi-window scope its own cell, row by row
  - `BTTCycleSteps` *(v3)*: string - running the action again on a window that is still where it was placed cycles through these grid cells, e.g. `"1/2, 1/3, 2/3"` (each step: `column[-lastColumn]/columns[:row[-lastRow]/rows]`). Implies grid placement
  - `BTTDirectionToMove`: number - `1` = left, `2` = right, `3` = above, `4` = below, `5` = next (system order), `6` = previous (system order)
  - `BTTChangeXOrigin` / `BTTChangeYOrigin`: number (`1`/`0`) - reposition horizontally / vertically. Axes that are not repositioned keep their relative position when the window moves to another monitor
  - `BTTOriginToUse`: number - which point of the window is placed: `0` = center, `1` = top left, `2` = top right, `3` = bottom left, `4` = bottom right, `5` = top edge center *(v3)*, `6` = bottom edge center *(v3)*, `7` = left edge center *(v3)*, `8` = right edge center *(v3)*
  - `BTTScreenOrigin`: number - where that point is placed: `0` = center, `1` = top left, `2` = top right, `3` = bottom left, `4` = bottom right corner of the reference area, `5` = mouse cursor position, `6` = the window's current position, `7` = top edge center *(v3)*, `8` = bottom edge center *(v3)*, `9` = left edge center *(v3)*, `10` = right edge center *(v3)*
  - `BTTChangeXOriginRelative` / `BTTChangeYOriginRelative`: number - offset unit: `0` = pixels, `1` = % of the reference (monitor) size, `2` = % of window size
  - `BTTNewXAbsolute` / `BTTNewYAbsolute` (unit `0`) or `BTTNewXRelative` / `BTTNewYRelative` (units `1`/`2`): number - the offset. X: positive = right. Y: positive = UP (legacy storage semantics; the form shows positive = down)
  - `BTTChangeWindowWidth`: number (`1`/`0`) - change the width. `BTTChangeWidthRelative`: `0` = fixed px (`BTTNewWindowWidthAbsolute`), `1` = % of monitor width (`BTTNewWindowWidthRelative`, optional px addition `BTTNewWindowWidthAbsoluteAddition`), `2` = fill remaining space (`BTTFillRight`: `1` or `BTTFillLeft`: `1`), `3` = grow/shrink by `BTTAddToWidth` in unit `BTTWidthChangeUnit` (`0` = px, `1` = % of current width)
  - `BTTChangeWindowHeight`: number (`1`/`0`) - change the height. `BTTChangeHeightRelative`: `0` = fixed px (`BTTNewWindowHeightAbsolute`), `1` = % of monitor height (`BTTNewWindowHeightRelative`, optional `BTTNewWindowHeightAbsoluteAddition`), `2` = fill remaining space (`BTTFillBottom`: `1` or `BTTFillTop`: `1`), `3` = grow/shrink by `BTTAddToHeight` in unit `BTTHeightChangeUnit` (`0` = px, `1` = % of current height)
  - `BTTDeltaKeepsAnchor` *(v3)*: number (`1`/`0`) - grow/shrink around the window anchor (`BTTOriginToUse`) instead of the top-left corner
  - `BTTMinWidth`, `BTTMaxWidth`, `BTTMinHeight`, `BTTMaxHeight` *(v3)*: numbers - size limits in px (`0` / absent = none), applied last while keeping the window anchor in place. `BTTAspectRatio` *(v3)*: string like `"16:9"`
  - `BTTToggleRestore` *(v3)*: number (`1`/`0`) - running the action again on a window that is still where it was placed restores its previous size & position
  - `BTTWindowScope` *(v3)*: number - `0` = only the selected window, `1` = all windows of the focused app, `2` = all windows on the target monitor
  - `BTTConstrainToScreen` *(v3)*: number (`1`/`0`) - keep the result inside the target monitor's visible area
  - `BTTUseVisibleFrame`: number (`1`/`0`) - take menu bar & Dock into account (use the visible area only)
  - `BTTCareForStageManager`: number (`1`/`0`) - take Stage Manager into account for calculations

Example (focused window: top left corner of its monitor, 50% of the monitor width, full remaining height):

  - `BTTWindowSwitcherShowThumbnail`: number - Thumbnail mode (0=app icon, 1=window thumbnail)
  - `BTTWindowSwitcherLayout`: number - Layout (0=vertical list, 1=horizontal thumbnails, 2=window previews only)
  - `BTTWindowSwitcherThumbnailWidth`: number - Thumbnail width in points, 100–400 (new actions: 150; fallback for already configured actions: 200)
  - `BTTWindowSwitcherThumbnailRows`: integer - Rows before scrolling, 1–10 (new actions: 2). One row scrolls horizontally; two or more wrap into a grid and scroll vertically after that many rows.   - `BTTWindowSwitcherSelectNextOnRepeat`: boolean - On repeated trigger, select next window in list
  - `BTTWindowSwitcherTriggerOnRelease`: boolean - Activate selected after releasing modifier keys (requires SelectNextOnRepeat)
  - `BTTWindowSwitcherVisibilityDelay`: number - Delay showing the switcher, popovers, and actual-window previews in milliseconds, clamped to 0–2000 (default/fallback: 0). Selection and keyboard handling start immediately; repeated triggers do not restart the delay. When modifier-release activation is enabled, releasing the modifiers before the delay ends activates the selection without showing the UI. Explicit activation, including Activate Hovered (476), also cancels pending presentation, even with `BTTWindowSwitcherKeepOpen` enabled. An empty search result does not close it. Ignored by the All Apps switcher (default: false)
  - `BTTWindowSwitcherCycleThroughWindowsOnly`: boolean - Repeated triggers and arrow keys skip the search field and cycle through windows only (new actions: true)
  - `BTTWindowSwitcherMousePos`: number - Position mode (0=mouse centered left, 1=mouse left to first item, 2=mouse left to second item, 3=centered on screen with mouse, 4=centered on screen with focused window, 5=custom position)

## Screenshot Actions

### Take Screenshot

> Takes a screenshot with configurable options.

Parameters:
* **BTTPredefinedActionType**: 169
* **BTTScreenshotOptions**: Screenshot configuration string (see below)
* **BTTScreenshotDateFormat**: Date format for the `{datetime}` placeholder in the file name (optional, e.g. "yyyy-MM-dd HH.mm.ss")

The options string is a `;;`-separated token list ending with the target file path (the path supports `{datetime}`, `{random}`, `~` and BTT variables). Tokens:
  - Capture mode (pick one):
    - `-i`: capture interactively. Modifiers: `-U` (show toolbar), `-w` (only window selection), `-W` (start in window selection mode), `-o` (no window shadow), `-S` (capture screen instead of window)
    - `-R;;x,y,w,h`: capture a specific screen rect (`-C` also captures the cursor)
    - `-l;;<window id>`: capture a specific window by CG window id (`-a` excludes attached windows)
    - Dynamic window targeting (resolved every time the action runs, same matching as action 364 "Activate Specific Window"): `BTTFindWindowTitle;;<regex>`, `BTTFindWindowApp;;<regex>`, `BTTFindWindowIndex;;<n>` (1 = topmost window, takes precedence over title/app), `BTTFindWindowFullScreenOnly`. Regex/wildcards work; BTT variables can be used inside curly braces. If nothing matches, an additional `-l;;<id>` serves as fallback, otherwise the capture is aborted.
    - no mode token: capture whole screen(s). Modifiers: `-m` (only main monitor), `-C` (capture cursor)
  - Misc: `-x` (no sounds), `-r` (no dpi metadata), `-c` (capture only to clipboard), `-T;;<seconds>` (delay), `-t;;<png|jpg|pdf|tiff>` (file format)
  - After capture: `BTTAdditionallyCopyToClipboard` (add `BTTDontCopyPath` to copy only the image, not the file path), `BTTEditInBTT`, `BTTUploadToImageKit` (`BTTUploadToImgur` is accepted for older presets), `BTTRunTerminalCommand`, `-u` (default macOS screenshot UI), `-M` (new mail), `-P` (open in Preview), `-B;;<bundle id>` (open with app)

Action chaining: when the options copy the capture to the clipboard (`-c` or `BTTAdditionallyCopyToClipboard`), BTT blocks the following actions in the same sequence until the capture has finished and the clipboard change has landed (max. 2 seconds grace; a cancelled interactive capture simply continues). Follow-up actions can therefore consume the clipboard directly. Exception: if the next enabled action is "Wait For Clipboard Change" (action 499) BTT does not wait itself, so that action can detect the change.

Example (capture the frontmost Safari window):
```json
{
  "BTTPredefinedActionType": 169,
  "BTTScreenshotOptions": "BTTFindWindowApp;;Safari;;-t;;png;;~/Pictures/Screenshot_{datetime}_{random}.png;;",
  "BTTScreenshotDateFormat": "yyyy-MM-dd HH.mm.ss"
}
```

### Wait For File Or Folder To Change

> Pauses an action sequence until the first matching new file or folder change is observed.

Parameters:
* **BTTPredefinedActionType**: 695
* **BTTAdditionalActionData**: JSON object with wait configuration
  - `BTTActionWaitForFileChangePaths`: string - Required file or folder paths, separated by `;;`. Use absolute paths or `~` for the home folder. BTT variables are resolved separately for each path when the action starts.
  - `BTTActionWaitForFileChangeType`: integer - Change type from the table below (default: 0, any change). Uses the same values as the File Or Folder Did Change trigger's `BTTFileChangeType`.
  - `BTTActionWaitForFileChangeTimeout`: number - Maximum wait in seconds, including setup (default: 60). `0` waits indefinitely; the maximum is `31536000` seconds (one year).
  - `BTTActionWaitForFileChangeContinueOnTimeout`: boolean - Continue without a matching change if the timeout expires (default: false).

Existing folders include changes in their subfolders. Paths may identify files or folders that do not exist yet, including missing intermediate folders: BTT watches the nearest existing parent for their creation. An item that already exists when monitoring begins does not satisfy a creation wait. Use a narrower folder or specific files for very large folder trees.

macOS can combine several filesystem operations into one event. A matching event reports a change; the producing app may still be writing the file. Observations use a bounded initial inventory (100,000 items, up to 10 seconds) and report an error if the folder cannot be inspected reliably or macOS reports lost events. Ancestor symlinks are resolved; a selected symlink is watched as a link, and symlinks inside a folder are not traversed.

Change types:

| Configuration value | Change | Result variable value |
|---|---|---|
| 0 | Any change | Actual change type below |
| 1 | Directory created | 0 |
| 2 | Directory removed | 1 |
| 3 | Directory renamed | 2 |
| 4 | Directory modified | 3 |
| 5 | File created | 4 |
| 6 | File removed | 5 |
| 7 | File renamed / moved into folder | 6 |
| 8 | File modified | 7 |
| 9 | File moved out of folder | 8 |

Result variables:

* **BTTFileChangeWaitResult**: `changed`, `timeout`, `cancelled`, or `error`.
* **BTTFileChangeWaitError**: Error description for `error`; empty for the other results.
* **BTTLastChangedFileOrFolder**: Matching path, updated only when the result is `changed`.
* **BTTLastChangedFileOrFolderChangedType**: Zero-based change type from the table, matching the trigger's result variable; `-1` means unknown. Updated only when the result is `changed`.

A matching change continues the sequence once. By default, a timeout stops the enclosing action sequence, including actions after an enclosing End If or End Repeat. Enabling `BTTActionWaitForFileChangeContinueOnTimeout` allows continuation on timeout. Invalid configuration or monitoring errors stop the enclosing sequence regardless of this setting.

Stop All Running Action Sequences cancels active file waits. Cancel Repeat cancels file waits within the selected repeat loop and preserves its usual continuation after End Repeat. The last changed path and type retain their previous values after timeout, cancellation, or error; check `BTTFileChangeWaitResult` when using timeout continuation.

### Find Text on Screen

> Runs OCR on the selected screen area, looks for the configured text and optionally moves the mouse to the match and runs named triggers.

Parameters:
* **BTTPredefinedActionType**: 426
* **BTTGenericActionConfig2**: string - the search configuration as a **JSON string** (a nested JSON object is not accepted for this action). It holds the following keys:
  - `BTTFindText`: string - the text to search for. BTT variables inside the string are resolved before searching
  - `BTTFindTextMatchMode`: number - how the text is compared against each recognized string: 1 = contains (default), 2 = begins with, 3 = ends with, 4 = equals, 5 = matches (regex)
  - `BTTFindTextSearchDirection`: number - order in which matches are sorted: 0 = left to right, then top to bottom; 1 = top to bottom, then left to right
  - `BTTFindTextRequiredOccurences`: number - which occurrence to use: 0 = the first match, n = the n-th match (1-based). If fewer matches are recognized, the search counts as failed
  - `BTTFindTextSearchOn`: number - which area is captured: 0 = all screens, 1 = screen with mouse cursor, 2 = main screen, 3 = screens without the mouse cursor, 4 = screen containing the focused window, 5 = only the focused window

  - `BTTFindTextMoveMouseTo`: number - 0 = do not move the mouse; any non-zero value moves the mouse to the matched text
  - `BTTFindTextIfFoundTrigger`: string - name of a named trigger to run when the text was found
  - `BTTFindTextIfNotFoundTrigger`: string - name of a named trigger to run when the text was not found
  - `BTTFindTextContinueActionExecution`: boolean - if true, the remaining actions still run when the text was not found

After execution, the following BTT variables are set:
* `last_find_text_on_screen_result`: JSON string with `recognizedText` and `boundingRects` arrays (empty string if no match)
* `last_find_text_on_screen_success`: `1` if the text was found (also `1` if not found but `BTTFindTextContinueActionExecution` is enabled), `0` otherwise

Example:
```json

  "BTTPredefinedActionType": 426,
```

### IF Condition

> Starts conditional block based on variable.

**How If blocks work** (applies to all IF actions: 330, 431, 705, 405, 428): the actions after the IF up to the matching "ELSE" (or "END IF" if there is no else) run when the condition is true, the actions between "ELSE" and "END IF" run when it is false. Afterwards the sequence continues after the matching "END IF". If blocks can be nested and can be placed inside repeat loops. Every IF should have a matching "END IF" on the same level. If an IF has no matching "END IF" (legacy structures, e.g. an else-if chain closed by a single "END IF" or none at all), BTT falls back to the pre-6.727 behavior: the If block simply runs to the end of the action list, and the "ELSE" branch is collected starting at the first "ELSE" encountered regardless of nesting (so the "ELSE" of an unclosed nested IF acts as the outer else). Always generate balanced IF / END IF pairs; the fallback only exists so old presets keep working. Only the first "ELSE" on a level is honoured; the actions after a second "ELSE" on the same level never run.

Parameters:
* **BTTPredefinedActionType**: 330
* **BTTIfConditionFormat**: Condition format string
* **BTTIfConditionData**: Condition data (base64 encoded)

Example:
```json
{
  "BTTPredefinedActionType": 330,
  "BTTIfConditionFormat": "myVar == 'true'",
  "BTTIfConditionData": "base64_encoded_data"
}
```

### IF JavaScript True

> Conditional based on JavaScript evaluation (BTT's built-in Core JavaScript engine, same as "Run Core JavaScript"). The script is evaluated asynchronously; the If block continues once the script has delivered its result. Booleans and the strings "true" / "false" are accepted, anything else counts as false.

Parameters:
* **BTTPredefinedActionType**: 431
* **BTTAdditionalActionData**: Object with:
  * **BTTAppleScriptString**: The JavaScript code
  * **BTTScriptFunctionToCall**: Name of the (async) function in the script that BTT calls; its return value is the condition result. If omitted, the script itself must hand the result back via `returnToBTT(true)` / `returnToBTT(false)`.
  * **BTTScriptType**: 3
  * **BTTActionJSRunInSeparateContext**: true to run in a separate JS context instead of the shared global one (optional)

**Note**: There is no "IF AppleScript True" action (type 432 exists internally but was never implemented and is not selectable). To use an AppleScript condition, run the AppleScript from within this JavaScript action (e.g. via `runAppleScript`) and return its result.

Example:
```json
{
  "BTTPredefinedActionType": 431,
  "BTTAdditionalActionData": {
    "BTTScriptType": 3,
    "BTTScriptFunctionToCall": "someJavaScriptFunction",
    "BTTAppleScriptString": "async function someJavaScriptFunction() {\n  let clipboard = await callBTT('get_clipboard_content', {});\n  return clipboard.length > 0;\n}"
  }
}
```

### IF AI Condition True

> Conditional that asks an AI model whether a statement about a piece of text is true. Requires macOS 13 or later. The evaluation runs asynchronously; the If block continues once the model has answered, the request timed out, or it was cancelled. Only the statement and the captured input are sent - no chat history, assistant instructions, skills or tools participate, and the input is treated as data, not as instructions.

Parameters:
* **BTTPredefinedActionType**: 705
* **BTTAdditionalActionData**: Object with:
  * **BTTActionAIConditionProfileUUID**: string - `BTTUUID` of the AI configuration to evaluate with (default `""`, which fails the evaluation). This is either a "Jev — AI Conditions" trigger (trigger type 877, configured in the AI section either with free access through BetterTouchTool's server or with your own TypeSafe API key) or an existing h@llo.ai assistant trigger whose `BTTAIAPIType` is one of `anthropic` / `anthropic-compatible` / `claude`, `openai-completion` / `openai` / `openai-compatible`, `openai-responses` / `openai-response` / `responses`, `openai-codex-oauth` / `chatgpt-codex` / `chatgpt-subscription`, or `apple-foundation` / `applefoundation` / `apple`. CLI-backed assistants are not supported. Disabled, duplicated or missing UUIDs make the evaluation fail; they are kept as-is on import/export so the reference can be repaired.
  * **BTTActionAIConditionStatement**: string - the statement or yes/no question to evaluate, e.g. "This text describes a programming error.". Required, max 4 KB.
  * **BTTActionAIConditionInputSource**: string - what to evaluate. One of `selectedText` (default), `clipboard`, `variable`, `text`, `activeApp`. `activeApp` sends a JSON object with the frontmost app's name, bundle identifier and (if available) focused window title.
  * **BTTActionAIConditionInput**: string - only used with `variable` (name of the BTT variable to read) and `text` (custom text; BTT variable placeholders like `{clipboard_content}` are replaced). Default `""`.
  * **BTTActionAIConditionTimeout**: number - seconds to wait for the model, 0.1 - 300 (default 15)
  * **BTTActionAIConditionFalseThreshold**: number - 0 - 1 (default 0.2). Probabilities at or below this count as false.
  * **BTTActionAIConditionTrueThreshold**: number - 0 - 1 (default 0.8). Probabilities at or above this count as true, values in between are uncertain. The false threshold must be lower than the true threshold. Both only apply to providers that return a probability (currently Jev); other models answer true / false / uncertain directly.
  * **BTTActionAIConditionUncertainPolicy**: string - what to do on an uncertain result: `stop` (default, stops the action sequence), `else` (run the else branch), `skip` (continue after "END IF")
  * **BTTActionAIConditionFailurePolicy**: string - same values, applied when the evaluation fails (invalid configuration, missing input, provider error, timeout). Default `stop`.

**Branching**: a true result runs the actions up to "ELSE", a false result runs the else branch (or continues after "END IF" if there is none). "Stop All Running Action Sequences" and "Cancel Repeat" always stop the block regardless of the policies above.

**Limits**: the captured input may be at most 64 KB; Jev additionally accepts at most 28 KB of input plus statement. Nothing is truncated - oversized input fails the evaluation and uses the failure policy.

**Jev connections**: a Jev profile (trigger type 877) can either use free access through BetterTouchTool's server or the user's own TypeSafe API key. This is stored in the profile trigger's `BTTAdditionalDataJSON` as the boolean `BTTAIDecisionUseBTTProxy` (only a real JSON boolean is accepted on import; when the key is absent the profile uses its own API key). Free access needs no API key and always uses the model `jev-1.13.0`, ignoring the profile's `BTTAIModel`. Either way, Jev evaluations only run after the user has confirmed the TypeSafe data privacy notice in the Jev configuration; that confirmation is stored locally per Mac, is not part of presets or exports, and until it is given every Jev evaluation fails and uses `BTTActionAIConditionFailurePolicy`. Profiles backed by h@llo.ai assistants are unaffected by this.

**Note**: the `BTTUIAICondition…` identifiers used by the configuration UI (Configure / Preview Input / Test Condition buttons and the "Advanced" disclosure) are not part of the trigger JSON.

Example:
```json
{
  "BTTPredefinedActionType": 705,
  "BTTAdditionalActionData": {
    "BTTActionAIConditionProfileUUID": "880216EF-BC84-447C-B32A-77CB159B9DAD",
    "BTTActionAIConditionStatement": "This text describes a programming error.",
    "BTTActionAIConditionInputSource": "clipboard",
    "BTTActionAIConditionTimeout": 15,
    "BTTActionAIConditionFalseThreshold": 0.2,
    "BTTActionAIConditionTrueThreshold": 0.8,
    "BTTActionAIConditionUncertainPolicy": "else",
    "BTTActionAIConditionFailurePolicy": "stop"
  }
}
```

### Find Position of Image on Screen

> Takes a screenshot of the selected area, searches it for a reference image (template matching) and optionally moves/drags the mouse to the match, saves its position to variables and runs named triggers depending on whether it was found.

Parameters:
* **BTTPredefinedActionType**: 291
* **BTTFindPositionOfImageImage**: string - base64 encoded PNG of the image to search for (this is the only way to supply the image; there is no file-path option)
* **BTTFindPositionOfImageImageDark**: string - base64 encoded PNG used instead while macOS dark mode is active. Only used when `BTTFindImageUseDifferentDarkModeImage` is true
* **BTTFindPositionOfImageConfig**: the search configuration, as a JSON object or JSON string. It holds the following keys:
  - `BTTFindImageUseDifferentDarkModeImage`: boolean - if true and dark mode is active, `BTTFindPositionOfImageImageDark` is used
  - `BTTFindImageUseColor`: boolean - include color in matching; if false, matching is done on grayscale
  - `BTTFindImageTreshold`: number 0.0 - 1.0 (note the spelling - this is the real key) - required match certainty. Higher = stricter
  - `BTTFindImageSearchOn`: number - which area is captured and searched: 0 = all screens, 1 = screen with mouse cursor, 2 = main screen, 3 = screens without the mouse cursor, 4 = screen containing the focused window, 5 = only the focused window's rect, 6 = square area around the mouse cursor (size from `BTTFindImageSquareSize`)
  - `BTTFindImageSquareSize`: number - edge length in points of the square centered on the mouse cursor (only for `BTTFindImageSearchOn: 6`)
  - `BTTFindImageSearchRegion`: number - further restricts the captured area: 0 = whole area, 1-4 = top left / top right / bottom left / bottom right quarter, 5 = top half, 6 = bottom half, 7 = left half, 8 = right half
  - `BTTFindImageSearchDirection`: number - order in which matches are collected: 0 = top left to bottom right, 1 = top right to bottom left, 2 = bottom left to top right, 3 = bottom right to top left
  - `BTTFindImageSkipFirstMatches`: number or string - skip this many matches and use the next one (a string may contain BTT variables)
  - `BTTFindImageMoveMouseTo`: number - where to move the mouse when found: 0 = do not move, 1 = top left of the match, 2 = center, 3 = top right, 4 = bottom left, 5 = bottom right
  - `BTTFindImageBTTMouseMoveDuration`: number - mouse move animation duration in seconds (0 - 3)
  - `BTTFindImageBTTMouseMoveDragType`: boolean - if set, the mouse is dragged (button held) instead of just moved
  - `BTTFindImageSaveToVariable`: boolean - save the found location to BTT variables (see below)
  - `BTTFindImageIfFoundTrigger`: string - name of a named trigger to run when the image was found
  - `BTTFindImageIfNotFoundTrigger`: string - name of a named trigger to run when the image was not found
  - `BTTFindImageContinueActionExecution`: boolean - if true, the remaining actions still run when the image was not found

When `BTTFindImageSaveToVariable` is enabled, the following BTT variables are set:
* `image_location`: the point as a string, e.g. `{100, 200}`
* `image_location_x`, `image_location_y`: the coordinates as numbers
* `image_location_found`: `1` when found, `0` when not found

Note: do **not** put this configuration into `BTTAdditionalActionData` for this action - for action 291 that would overwrite the stored image data.

Example:
```json
{
  "BTTPredefinedActionType": 291,
  "BTTFindPositionOfImageImage": "iVBORw0KGgoAAAANSUhEUg...",
  "BTTFindPositionOfImageConfig": {
    "BTTFindImageUseColor": true,
    "BTTFindImageTreshold": 0.85,
    "BTTFindImageSearchOn": 1,
    "BTTFindImageSearchRegion": 0,
    "BTTFindImageSearchDirection": 0,
    "BTTFindImageMoveMouseTo": 2,
    "BTTFindImageBTTMouseMoveDuration": 0.2,
    "BTTFindImageSaveToVariable": true,
    "BTTFindImageIfNotFoundTrigger": "Image Missing Handler"
  }
}
```

### Interact with UI Element

> Generic UI element interaction using accessibility (AX) paths.

Parameters:
* **BTTPredefinedActionType**: 522
* **BTTGenericActionConfig**: AX path copied from BTT's UI element viewer
* **BTTActionInteractWithUIElementAction**: Action type
* **BTTActionInteractWithUIElementBringToFront**: Bring to front flag
* **BTTActionInteractWithUIElementOnlyFocusedWindow**: Only focused window
* **BTTActionInteractWithUIElementOptions**: Additional options
* **BTTAdditionalActionData**: JSON object with AX path configuration
  - `BTTVariableName`: string - Variable to write to, for the `AXSaveDescriptionToVariable` / `AXSaveValueToVariable` action types
  - `BTTActionAXValue`: string - Value to write, for the `AXSetValue` action type

Built-in action types (`BTTActionInteractWithUIElementAction`, stored in
`gesture.additionalActionString`). Any other value is performed as a raw AX action name
(e.g. `AXPress`):
- `AXMoveMouseToCenter` (default) - move the cursor to the element
- `AXSaveDescriptionToVariable` - write the element's full description (JSON) to `BTTVariableName`
- `AXSaveValueToVariable` - write the element's `AXValue` to `BTTVariableName`
- `AXSetValue` - **set** the element's `AXValue` to `BTTActionAXValue`

`AXSetValue` converts to whatever type the element already holds (number, boolean or
string), so it drives sliders, steppers, checkboxes and text fields. `BTTActionAXValue`
supports variables, and can be driven by an action value binding — making this the general
way to control any app's UI from a slider, knob or MIDI fader.

Replace the illustrative paths below with paths copied from BTT's UI element viewer. The AX path and focus flags are top-level properties.

Example (set a slider from the trigger's value):
```json
{
  "BTTPredefinedActionType": 522,
  "BTTActionInteractWithUIElementAction": "AXSetValue",
  "BTTAdditionalActionData": {
    "BTTActionAXValue": "0.5"
  },
  "BTTActionValueBindings": {
    "BTTActionAXValue": {
      "source": "normalized",
      "outMin": 0,
      "outMax": 1
    }
  },
  "BTTGenericActionConfig": "Application{\"ExampleApp\"} -> AXWindows[0]Window{\"Main\"} -> AXChildren[2]Slider{\"Volume\"}"
}
```

Example:
```json
{
  "BTTPredefinedActionType": 522,
```

### Remove Website(s) from Safari History & Cache

> Experimental. Removes local Safari history entries and HTTP disk cache records for specific website domains. Default Safari profile only. Cookies, logins, local storage, service-worker caches and shared cache blobs are preserved. Other devices may restore history through iCloud; this action does not synchronize deletions. Full Disk Access may be required.
>
> A preview can run while Safari is open and never prompts. Actual removal requires Safari to be quit: with `BTTActionSafariCleanupWaitForQuit` enabled and Safari running, BTT shows a dialog offering to quit Safari or to run the cleanup later, and the request is queued until Safari has quit. With the option disabled the action fails immediately while Safari is running. Pending requests expire after 24 hours or when BTT quits, and at most 32 requests can wait at once. Re-running the same trigger replaces its own pending request. Subsequent actions in a sequence continue once the request is accepted; the final outcome is reported through variables.

Parameters:
* **BTTPredefinedActionType**: 694
* **BTTAdditionalActionData**: JSON object with configuration
  - `BTTActionSafariCleanupDomains`: string - Website domains, one per line (commas also accepted), e.g. `example.com`. Between 1 and 100 domains. Entries are canonicalized to a host; page paths, wildcards, ports, credentials, queries and fragments are rejected, and a bare public suffix such as `co.uk` is not accepted.
  - `BTTActionSafariCleanupHistory`: boolean - Remove local history (default: true). History and cache may not both be false.
  - `BTTActionSafariCleanupCache`: boolean - Remove HTTP disk cache records (default: true)
  - `BTTActionSafariCleanupIncludeSubdomains`: boolean - Also match subdomains of the listed domains (default: true)
  - `BTTActionSafariCleanupPreviewOnly`: boolean - Report matching items without removing anything (default: true)
  - `BTTActionSafariCleanupWaitForQuit`: boolean - Shown in the UI as "Prompt to Quit Safari or Run Later" (default: true). When a non-preview run finds Safari (and/or Safari Technology Preview) running, BTT shows a dialog with a quit button and a "Later" button; quitting is requested as normal application termination and Safari may refuse or cancel it. "Later" (also Escape) keeps the request queued without prompting again, until Safari is quit manually. Cleanup starts once all Safari processes are closed, after a short grace period. With this option disabled the action fails while Safari is running instead of queueing.
  - `BTTActionSafariCleanupNotify`: boolean - Show a notification with the result (default: true). Failures are always reported.

Results are written to the variables `safari_cleanup_status` (`queued`, `running`, `preview`, `completed` or `failed`) and `safari_cleanup_result` (JSON with `status`, `message`, `previewOnly`, `domains`, `historyItems`, `historyVisits`, `cacheRecords`, `removedHistoryItems` and `removedCacheRecords`).

Example (preview which entries would be removed, while Safari is running):
```json
{
  "BTTPredefinedActionType": 694,
  "BTTAdditionalActionData": {
    "BTTActionSafariCleanupDomains": "example.com\nexample.org",
    "BTTActionSafariCleanupHistory": true,
    "BTTActionSafariCleanupCache": true,
    "BTTActionSafariCleanupIncludeSubdomains": true,
    "BTTActionSafariCleanupPreviewOnly": true,
    "BTTActionSafariCleanupWaitForQuit": true,
    "BTTActionSafariCleanupNotify": true
  }
}
```

Example (remove history only, prompting to quit Safari and queueing until it has quit):
```json
{
  "BTTPredefinedActionType": 694,

    "BTTActionSafariCleanupDomains": "example.com",
```

#### How an assistant reference is resolved (525 and 581)

- With `BTTAIChatIdentifier` set, the action is a reference: BTT loads the referenced assistant's stored configuration and then applies the action's own values for the override keys `BTTAIChatIdentifier`, `BTTAIInitialUserMessage`, `BTTAISInitialScreenshot`, `BTTAICloseAfterProcessingUserMessage`, `BTTAIInvisibleMode`, `BTTAIUserMessage`, `BTTAIUserMessageFileType`, `BTTAIShowProgressIndicator`, `BTTAIShowStatusMessages`, `BTTAIBackgroundReuseConversation`, `BTTAIActiveSkills`, `BTTAIOptionalSkills`, `BTTAIDisabledSkills` and `BTTAIForceExpandedOnOpen` on top of it.
- Any *other* key starting with `BTTAI` (for example `BTTAIModel`, `BTTAISystemPrompt`, `BTTAIAPIType` or a context/tool flag) makes the action a legacy inline configuration instead. It is then used as-is, and action 525 may migrate it into a new assistant trigger and rewrite itself into a reference.
- Keys that do not start with `BTTAI` do not influence this decision. Settings left over from a previously configured action type (for example `BTTChatGPT…` keys) are ignored and are never merged into the resolved assistant configuration.
- The API key is looked up in the Keychain for the referenced assistant first, then for the action itself. It is never part of the action JSON.

### Codex Controller Actions

> Overview of the Codex Controller action family (605-614). BetterTouchTool uses a Codex app-server for task discovery, creates new tasks through the ChatGPT/Codex desktop composer, and forwards existing-task operations to the desktop app so both surfaces stay on the same live task. All actions require macOS 13.0 or later.

Shared behavior:
- All configuration lives in `BTTAdditionalActionData`.
- BTT variables can be used in all text fields - they are resolved before the operation runs.
- **Target Task** (`BTTActionCodexTarget`): `active` (default), or `slot:1` through `slot:6`. Use `custom` together with `BTTActionCodexThreadID` only when a fixed thread ID is required.
- **Result Variable** (`BTTActionCodexResultVariable`): name of the BTT variable that receives the JSON result of the operation. Defaults to `BTTLastCodexControllerResult`. The JSON result contains a `success` field.
- Live Codex data is additionally exposed through the `BTT_CodexController…` variables and `BTT_CodexControllerSnapshot`.
- Refresh reads the most recent non-archived desktop/app-server, CLI, and VS Code tasks from the shared Codex thread store; sub-agent threads are excluded from the six menu slots.
- Start, Send, Stop, Approve, and Decline require the ChatGPT/Codex desktop app to be running. Start and Send open the target task automatically when the app does not already own its live stream.
- Start Task with a prompt requires BetterTouchTool's macOS Accessibility permission so BTT can focus and submit the native Codex composer.
- BTT prefers the Codex app-server bundled with ChatGPT so its desktop coordination protocol stays version-aligned. Set the `BTTCodexCLIPath` user default only when an explicit CLI override is required.
- Desktop synchronization uses ChatGPT's local renderer-coordination protocol. That protocol is currently private and version-dependent, so a future ChatGPT update may require a corresponding BetterTouchTool update.

Floating Menu building blocks:
- Run **Refresh Tasks** before showing the menu, or from a small refresh item.
- Create up to six task items. Item N displays `{BTT_CodexControllerThreadNTitle}` and triggers **Agent Key** with Target Task set to Task Slot N. One tap selects the task without activating Codex; a second tap within the macOS double-click interval brings Codex to the front.
- Set **Visible Only If Variable Is True** to `BTT_CodexControllerThreadNAvailable` (without braces) to hide empty slots. Use `BTT_CodexControllerThreadNIsActive` in visibility or content scripting when the selected slot needs distinct styling.
- Set Open, Stop, Send, Fork, Approve, and Decline menu items to **Active Task**. Selecting an Agent Key changes which task those shared controls affect.
- `BTT_CodexControllerThreadNVisualStatus` is normalized to `off`, `idle`, `thinking`, `complete`, `input`, or `error`. The controller intentionally publishes no colors or menu-property JSON; appearance is owned by the user's named style triggers.
- `BTT_CodexControllerAppearanceRevision` changes after the six semantic status and selection variables have been updated. A single **Variable Value Did Change** trigger can monitor it and apply user-editable named style triggers to all six items. Put **Update Floating Menu Item Properties** (447) in each style trigger, declare an `item_uuid` variable, and target `{item_uuid}` with **Persist Changes** disabled.
- Other per-slot data is available as `BTT_CodexControllerThreadNStatus`, `BTT_CodexControllerThreadNContextPercent`, `BTT_CodexControllerThreadNNeedsApproval`, `BTT_CodexControllerThreadNIsWorking`, `BTT_CodexControllerThreadNCanStop`, and `BTT_CodexControllerThreadNLastMessage`. `BTT_CodexControllerActiveSlot` is 1-6, or 0 when no slot is active.
- The selected task is mirrored through `BTT_CodexControllerActiveAvailable`, `BTT_CodexControllerActiveTitle`, `BTT_CodexControllerActiveStatus`, `BTT_CodexControllerActiveContextPercent`, `BTT_CodexControllerActiveNeedsApproval`, `BTT_CodexControllerActiveIsWorking`, `BTT_CodexControllerActiveCanStop`, and `BTT_CodexControllerActiveLastMessage`. These are convenient for shared status, Stop, and approval controls. Use `ActiveCanStop`, not merely `ActiveIsWorking`, for the Stop item's visibility.
- The selected task also exposes `BTT_CodexControllerActiveVisualStatus`.

### Generic Configuration Fields

When specific property names aren't mapped for an action, these generic fields are used as fallbacks:
- `BTTGenericActionConfig`: Primary configuration string/JSON (used when gesture.launchPath isn't specifically mapped)
- `BTTGenericActionConfig2`: Secondary configuration (used when gesture.additionalActionString isn't specifically mapped)
- `BTTAdditionalActionData`: Complex data as JSON or base64 (typically from gesture.actionData)

### Action Value Bindings

Supported numeric action fields can be driven by the **value of the trigger that fired
the action** — a floating menu slider or knob, an incoming MIDI CC, a mouse drag, or a
continuous trackpad gesture — instead of a fixed stored number. See [Action Value
Bindings](/docs/actions/value-bindings) for setup through the UI; the JSON format is
described below.

* **BTTActionValueBindings**: JSON object mapping a field to a binding descriptor.

The key is either a key inside `BTTAdditionalActionData` (e.g. `BTTMidiCommandValue`) or a
generic-config field name — `launchPath` (`BTTGenericActionConfig`) or
`additionalActionString` (`BTTGenericActionConfig2`).

Binding descriptor properties:
* **source**: `"value"` (**Set Value Directly**; raw value in the trigger's units, default when omitted from JSON), `"normalized"` (**Advanced → Position (0…1)**), `"delta"` (**Advanced → Change Since Last Update**), or `"accumulated"` (**Increase / Decrease Value**; see below). New UI bindings for continuous trackpad gestures and mouse drags select `"accumulated"`; saved bindings and the JSON default are unchanged.
* **inMin** / **inMax**: input range; defaults to the trigger's range for `"value"`, 0–1 for `"normalized"`, and 0 to the trigger's range span for `"delta"`. The `"accumulated"` source uses `fullScaleDelta` instead.
* **outMin** / **outMax**: output range. The UI fills these from the field's declared range; if omitted from a JSON descriptor, they default to 0 and 1.
* **curve**: `"linear"` (default), `"invert"`, `"log"`, `"exp"`
* **round**: `"none"` (default), `"int"`, `"step"`
* **step**: step size when `round` is `"step"`
* **clamp**: boolean, default `true` — keeps the result inside the output range

Example — a floating menu slider driving MIDI CC 11:
```json
{
  "BTTPredefinedActionType": 462,
  "BTTAdditionalActionData": {
    "BTTMidiCommandType": 191,
    "BTTMidiCommandControllerNumber": 11,
    "BTTMidiCommandChannel": 0
  },
  "BTTActionValueBindings": {
    "BTTMidiCommandValue": {
      "source": "value", "outMin": 0, "outMax": 127, "round": "int", "clamp": true
    }
  }
}
```

Triggers that currently publish a value:

| Trigger | Range | Notes |
|---|---|---|
| Floating menu slider | its configured min/max (default 0-1) | under the Value Changed / Value Change Ended categories |
| Floating menu knob | its configured min/max (default 0-100) | value categories, plus the rotate categories |
| MIDI triggers | 0-127 | any action under the trigger |
| Mouse drag (discrete + continuous) | 0-100 | how far along the current stroke; `delta` carries the signed movement represented by this action execution, in pixels (up/right positive). Use `"accumulated"` to increase/decrease the current or remembered value. |
| Continuous trackpad swipe or edge slide | 0-100 | While Moving, continuous direction and Gesture End categories. `delta` is signed movement in percentage points of trackpad width/height (up/right positive). Use `"accumulated"` to keep adjusting a value through reversals. |
| Continuous pinch or rotation | 0-100 | While Pinching/Rotating, their direction and Gesture End categories. `delta` uses magnification percentage points for pinch (out positive) or degrees for rotation (counterclockwise positive). |

#### Accumulating Source (Increase / Decrease Value)

`"source": "accumulated"` is shown as **Increase / Decrease Value** in the UI.
It adds the trigger's signed movement to the current or remembered value and keeps
that value between gestures. This is what makes "drag up = louder, drag down = quieter" work: a mouse
drag reports distance travelled *within the current stroke*, so a plain `"value"` binding
would jump back to the start of the range every time a new drag begins.

Additional properties:
* **fullScaleDelta**: how much raw movement sweeps the entire range. Defaults per trigger: 40 (continuous swipes/edge slides, in percentage points of trackpad width/height), 50 (pinch magnification percentage points), 90 (rotation degrees), 200 (mouse drag, in pixels — matching BetterTouchTool's usual 200px = 100%), 127 (MIDI), 100 (knob). Larger = less sensitive.
* **accumulateStart**: starting position within the output range when the target's current value cannot be read, 0-1. Default `0.5`.
* **accumulateWrap**: boolean, default `false`. `true` wraps past the ends instead of stopping at them.

The position is per trigger *and* per bound field, is kept in memory only (it resets when
BetterTouchTool restarts), and dragging down lowers the value without needing an inverted
curve — unlike `"value"`, which is unsigned. Setting `curve` to `"invert"` therefore
reverses the direction again; leave it `"linear"` unless you want to reverse the movement direction.

Continuous trackpad bindings additionally separate remembered values by bound action, device,
axis and category. Use one action under **While Moving (Continuous)** for one value controlled in both directions; separate directional actions have separate retained positions.

For actions whose current value can be read — **Set Volume**, **Set Brightness**, **Set
Keyboard Brightness** and **Set Audio Input Volume** — the binding adopts the real current
value when you pick the control up again: continuous trackpad gestures use a new gesture
session, while mouse drags refresh after an idle pause. This lets the binding follow changes
made by other means (media keys, another app) in between.
`accumulateStart` is only used for actions whose value cannot be read.

Example — mouse drag up/down to increase/decrease volume (assign to both the Drag Up and Drag Down
continuous categories):
```json
{
  "BTTPredefinedActionType": 373,
  "BTTGenericActionConfig": "50",
  "BTTActionValueBindings": {
    "launchPath": {
      "source": "accumulated",
      "outMin": 0, "outMax": 100,
      "fullScaleDelta": 400,
      "round": "int"
    }
  }
}
```

The same values are also exposed as variables for string fields and scripts:
`BTTTriggerValue`, `BTTTriggerValueNormalized` (0-1), `BTTTriggerValuePercent` (0-100),
`BTTTriggerValueMIDI` (0-127), `BTTTriggerValueDelta`, `BTTTriggerSourceUUID`,
`BTTTriggerSourceIdentifier`, `BTTTriggerSourceKind`.

### Keyboard Clean Mode (Lock Keyboard & Trackpad For Cleaning)

> The modern successor of the KeyboardCleanTool, built into BTT. Locks the keyboard (incl. media/function keys and, on Touch Bar Macs, the Touch Bar via a system-modal "locked" bar) and optionally trackpad & mouse clicks/scrolling/gestures (the cursor may still move - macOS does not allow blocking that) so they can be wiped without triggering anything, darkens all screens (a black screen makes smudges visible) and shows a status card with unlock instructions. ### Run Swift Script

> Compiles and runs a Swift script. Requires the Xcode Command Line Tools (`swiftc`) on the Mac. The source is compiled once into a cached library (`~/Library/Application Support/BetterTouchTool/SwiftScriptCache`, keyed by a content hash), so only the first run after an edit takes a few seconds - later runs take milliseconds. The script is compiled as a library: no top-level statements; it must define `func run(_ btt: BTTScript) async throws -> Any?` (`async` / `throws` are optional). `run` is called on the main actor and its return value (String, number, Bool, `[String: Any]`, `[Any]` or nil) becomes the action result (e.g. the reply of `trigger_named`; dictionaries / arrays are returned as JSON). BTT variable placeholders are NOT substituted into the source - use the `btt` object instead: `await btt.getVariable(name)` / `getString` / `getNumber`, `await btt.setVariable(name, value, persist: false)`, `try await btt.triggerNamed(name)`, `await btt.triggerNamedAsync(name)`, `try await btt.call(route, params)` (any BetterTouchTool scripting route such as `get_clipboard_content`, `display_notification`, `update_menu_item`), `btt.log(message)`, plus `btt.triggerUUID`, `btt.triggerName`, `btt.presetPath` and `btt.runsInsideBetterTouchTool`. Two execution modes: "Separate process" (default; runs in BetterTouchToolSwiftScriptRunner.xpc, crash-isolated, a timeout terminates the runner) and "Inside BetterTouchTool" (fastest, direct access to the app; no timeout possible and a crashing script crashes BetterTouchTool).

Parameters:
* **BTTPredefinedActionType**: 691
* **BTTAdditionalActionData**: Object with:
  * **BTTScriptString**: Swift source code (must define `run`)
  * **BTTScriptType**: 5
  * **BTTScriptLocation**: 0 = inline source (default), 1 = file inside the preset folder, 2 / 3 = external file (path in `BTTScriptExternalPath`)
  * **BTTSwiftScriptExecutionMode**: 0 = separate process (default), 1 = inside BetterTouchTool
  * **BTTSwiftScriptTimeout**: timeout in seconds as a string, "0" = none (separate process only)
  * **BTTSwiftScriptOptimize**: true compiles with `-O` (default false, `-Onone`)

Example:
```json
{
  "BTTPredefinedActionType": 691,
  "BTTAdditionalActionData": {
    "BTTScriptType": 5,
    "BTTScriptLocation": 0,
    "BTTSwiftScriptExecutionMode": 0,
    "BTTSwiftScriptTimeout": "10",
    "BTTScriptString": "import Foundation\nimport AppKit\n\nfunc run(_ btt: BTTScript) async throws -> Any? {\n    let app = NSWorkspace.shared.frontmostApplication?.localizedName ?? \"unknown\"\n    await btt.setVariable(\"frontApp\", app)\n    return app\n}"
  }
}
```

Script mode (top-level code): if the source does NOT define a top-level `func run(_ btt: BTTScript)`, BetterTouchTool treats the text like `swift file.swift` - the code is compiled as an executable (`main.swift`; a leading `#!` line is ignored, line numbers in diagnostics stay unchanged) and it always runs as a child process of the separate runner (the "Inside BetterTouchTool" option is ignored, a note is logged). The trimmed standard output becomes the action result; a non-zero exit code or stderr output is reported as an error (`Swift script error: The script exited with code N: …`) - when stdout was produced anyway, it is still returned and the problem is only logged. `BTTScript` is not available in this mode; the environment variables `BTT_PRESET_PATH`, `BTT_TRIGGER_UUID` and `BTT_TRIGGER_NAME` are set and the working directory is the preset folder. Detection is based purely on the source text, so inline scripts work exactly like external files. Example:
```json
{
  "BTTPredefinedActionType": 691,
  "BTTAdditionalActionData": {
    "BTTScriptType": 5,
    "BTTScriptLocation": 0,
    "BTTSwiftScriptTimeout": "10",
    "BTTScriptString": "import Foundation\nlet name = ProcessInfo.processInfo.environment[\"BTT_TRIGGER_NAME\"] ?? \"?\"\nprint(\"Hello from \\(name)\")"
  }
}
```

### Snap Menu Actions (Editable Window Snapping Menus)

> Context-relative snapping actions for the items of a window snapping menu. While a window is dragged to a screen edge / corner or to the edge of another window, BetterTouchTool can reveal a small menu of nearby layout options ("Show nearby snapping options while dragging" in Settings → Window Snapping & Moving). The items of these menus are configured with the "Snap Menu: …" other triggers, whose automatically assigned action opens the item editor. Each of these actions applies one destination that is derived from the encounter that opened the menu - the dragged window, the screen, the target window and the position where the menu appeared - instead of a fixed rectangle.

Parameters:
* **BTTPredefinedActionType**:
  - Apply Normal Snap for Current Position: 698 - applies the normal snapping destination for the screen or window position that opened the menu.
  - Snap to Upper / Left Segment of Target: 699 - uses the upper segment at a left or right window edge, or the left segment at a top or bottom window edge. At the inside top-center position this is the target window's left half.
  - Snap to Unsplit Target Edge: 700 - uses the unsplit destination for the current target-window edge, without selecting an upper, lower, left or right corner segment.
  - Snap to Lower / Right Segment of Target: 701 - uses the lower segment at a left or right window edge, or the right segment at a top or bottom window edge. At the inside top-center position this is the target window's right half.
  - Snap to Opposite Segment of Target: 702 - uses the other end of the current target-window edge when the menu opened near a corner. From the middle of an edge it uses the upper or left segment.
  - Use Other Fill Mode Beside Target: 703 - switches between matching the target window's width / height and filling the full screen extent. Only available when snapping outside a target window's edge, and it respects the fill mode selected with ⌥ (opt).
  - Fill to Next Window: 704 - fills the available space from the screen edge or corner that opened the menu up to the next fully visible neighboring window. Works with "Snap to other windows" disabled; no destination is captured when there is no suitable neighbor.
* No additional configuration required, these actions have no `BTTAdditionalActionData` keys.

Notes:
* The actions run when the dragged window is released, never while hovering. They can be combined with other actions in the same item's action sequence (before or after the snap action).
* Outside of a snapping-menu context they do nothing, so they are not useful on normal triggers like keyboard shortcuts.
* 699-703 only produce a destination for the window-relative positions ("Snap Menu: Window …" triggers, which require "Snap to other windows" to be enabled). At a screen edge or corner, 698 and, when a suitable neighbor exists, 704 have captured destinations. Action 704 respects window spacing and uses the largest clear rectangle anchored at a corner.
* Ordinary window actions can be used in snapping menu items as well. When executed from such an item they act on the window that is being dragged instead of the focused window - this includes the built-in position actions and Custom Move / Resize (251).

Example:
```json
{
  "BTTPredefinedActionType": 699
}
```
